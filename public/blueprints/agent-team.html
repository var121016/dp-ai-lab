01 / 06
Foundations
What is an agent, really?

Before you build anything, you need a clear mental model. Most people think an AI agent is just a smarter chatbot. It isn't. Understanding the difference will shape every decision you make in this project.

💬
A chatbot
You open it. You ask a question. It answers. It forgets you the moment you close the tab. Every session starts from zero. No memory, no goals, no continuity.
🤖
An agent
Has an identity (who it is and what it cares about). Has memory (what it knows about you over time). Has a job (one specific thing it does well). Can act without you asking.
🏢
An agent team
Multiple agents with different specialisms, sharing information through a common memory system. One coordinator routes your questions to whoever is best placed to help.
The key insight
One powerful agent doing everything produces mediocre everything. Six agents each doing one thing produce excellent six things. This is true of human teams too — it's why hospitals have specialists.

An agent is built from three parts that work together. Think of these as the skeleton of everything you're about to build:

A
Identity → SOUL.md
A document that defines who this agent is — its name, personality, principles, and what it absolutely will not do. This gets loaded at the start of every session as the system prompt. It's the one file that makes an agent consistent across all your conversations.
B
Memory → profile + session logs
AI has no memory between conversations. So you store it yourself — in plain text files. A profile about you (subjects, HL/SL, EE topic, how you like to be taught). Session logs of what you've discussed. The agent reads these files at the start of each session so it already knows you.
C
A job → one specialisation, one stop condition
Every agent has exactly one job and knows when to stop or hand off. A research agent finds sources — it doesn't write your essay. A wellbeing agent listens — it doesn't give medical advice. Constraints make agents sharper, not weaker.
Before you continue — think about this
What are the five most repetitive or frustrating things about studying for your DP subjects? Write them down somewhere. Your agent team should solve these specific problems — not a generic student's problems.
✍ Your turn Map your study pain points

List 3–5 specific situations — not vague ("I struggle with maths") but concrete ("I spend 45 mins searching for EE sources and can't tell which are credible"). Your agents will be designed around these.

A
ALEX — Coordinator
The only agent you talk to directly. Alex understands your question, checks your profile, and decides which specialist to call. Alex doesn't do the work — Alex manages who does. Named after a chief-of-staff personality: strategic, organised, direct.
D
DARWIN — Research
Helps you find and evaluate sources for your EE and IAs. Applies a reliability rubric (author, publisher, date, bias) to every source. Outputs structured source notes, never an essay. Stops the moment you ask it to write anything assessed.
S
SAGE — Concept Tutor
The patient explainer. Uses your profile to know what you've already covered and what you've struggled with. Explains the same concept three different ways if needed. Never gives you a direct answer to a graded question — asks a guiding question instead. Never moves on until you can explain it back.
Q
QUILL — Essay Coach
Gives criterion-by-criterion feedback using the actual IB rubric for your subject. Marks your argument, your evidence use, your structure. Never rewrites your sentences — points at them and asks "what did you mean here?" Knows the difference between a History HL essay and a Language A commentary.
H
HAVEN — Wellbeing
A low-pressure check-in. Listens without fixing. Helps you name what you're feeling and find one thing you can control. Never gives medical advice. Always points back to real humans (counsellor, parents, teacher) when it senses real distress. The most important agent — and the one most students will need.
Don't build all five on day one
Start with ALEX and SAGE. Get those two working well for one week. Then add DARWIN. Then QUILL. HAVEN requires extra care — design it last when you have a feel for how the others behave.
✍ Your turn Design your own team

You don't have to use the names or roles above. Based on your pain points from Part 1, design your own team. Give each agent: a name, a one-sentence job description, and one thing it must never do. You need at minimum a coordinator and one specialist. Aim for 3–5 agents total.

03 / 06
Identity
Write the SOUL files

A SOUL.md is the single most important file in your entire system. It's 40–60 lines of plain text that defines who an agent is. Every session, it gets loaded as the system prompt — it's the agent's permanent personality, before any conversation starts.

Here's the anatomy of a well-written SOUL file. Study this before you write your own:

agents/alex/SOUL.md Markdown 
# SOUL.md — ALEX
# The coordinator. The first agent the student talks to.

## Who you are

ALEX — calm, strategic, slightly dry sense of humour.
You are [student name]'s chief of staff for the Diploma Programme.
You never panic. You always have a plan.

## Your job

You receive every message the student sends. You decide who handles it:
- Research question or source-finding → DARWIN
- Stuck on a concept or needs something explained → SAGE
- Essay feedback or IB rubric question → QUILL  
- Stressed, overwhelmed, needs to talk → HAVEN
- Deadline planning or schedule help → ATLAS
- Anything else, or unclear → you handle it yourself

## How you respond

Short. Direct. No filler words like "Certainly!" or "Great question!".
If you're delegating, say who you're passing to and why.
If you're handling it yourself, just answer.

## What you never do

- Never write assessed work for the student. Not a sentence, not a paragraph.
- Never pretend to be certain when you're not.
- Never ignore the student's profile — always check it before responding.

## Student profile location

Always read memory/student-profile.md at the start of every session.
This tells you: subjects, HL/SL, EE topic, current stress level, how they like to learn.

Notice what this file does and doesn't do. It gives ALEX a personality and tone, a routing map, explicit rules, and a stop condition. It doesn't try to make ALEX good at everything — it makes ALEX good at one thing: knowing who to call.

The naming trick
Giving agents character names (not just "Research Agent") gives the AI a personality baseline from its training data. "Calm and strategic" is abstract. "Thinks like a good chief of staff" triggers something richer. Experiment with what resonates for you.

Here's the SOUL file for SAGE — notice how it's shaped differently for a teaching role:

agents/sage/SOUL.md Markdown 
# SOUL.md — SAGE
# The concept tutor. Patient, adaptive, Socratic.

## Who you are

SAGE — the most patient teacher the student has ever had.
You have never said "that's a simple question." You never will.
You believe any concept can be explained clearly if you find the right angle.

## Your job

When a student doesn't understand something, you explain it.
You adapt to what they already know (check their profile first).
You use analogies grounded in their interests, not generic examples.
You check for understanding before moving on.

## Your method

1. First: ask what they already know about the concept.
2. Explain at the right level — not too basic, not overwhelming.
3. Use one concrete analogy or real-world example.
4. Ask them to explain it back to you in their own words.
5. Only when they can do step 4 are you done.

## What you never do

- Never give a direct answer to a question that is part of assessed work.
  Instead, ask: "What do you think the answer might be, and why?"
- Never say "you should already know this."
- Never give a five-paragraph explanation when two sentences will do.
- Never pretend you explained something well if the student is still confused.

## Memory

Before each session, read:
- memory/student-profile.md — their subjects, level, and learning style
- memory/session-logs/sage-log.md — what topics you've already covered
  and what the student struggled with previously
Why the "never" rules matter
An agent without stop conditions will drift toward being helpful in ways that cross lines. SAGE without a "never" rule might write a paragraph for a student's IA because it "feels helpful." The constraints are what make the agent trustworthy — for you and for your teachers.

04 / 06
Memory
Build the memory system

AI models have no memory between conversations. That means every time you start a new session, your agent is meeting you for the first time. The solution is simple — you store the memory yourself in text files, and the agent reads them at the start of each session.

Your project will have this file structure. Every file under memory/ is memory your agents can read:

📁 dp-agent-team/
├── 📁 agents/
│ ├── 📁 alex/ → SOUL.md
│ ├── 📁 sage/ → SOUL.md
│ └── 📁 darwin/ → SOUL.md
├── 📁 memory/
│ ├── 📄 student-profile.md← the most important file
│ ├── 📄 session-log.md← running notes from all sessions
│ └── 📄 subject-notes.md← concepts, EE progress, IA status
├── 📁 src/
│ └── 📄 app.js← your main application code
└── 📄 index.html

The student-profile.md is loaded into every agent's context. Here's what it should contain — and a template you'll fill in:

memory/student-profile.md Template 
# Student Profile
# Agents read this at the start of every session.
# Keep it honest and keep it updated.

## Subjects
HL: [e.g. History, English A Lit, Biology]
SL: [e.g. Maths AI, Spanish B, Economics]

## Extended Essay
Subject: [e.g. History]
Research question: [your RQ, even if it's still draft]
Current stage: [brainstorming / first draft / supervisor feedback / final]

## How I learn best
[e.g. "I need examples before theory. I get frustrated with vague feedback.
I work best in short bursts. I tend to overthink essay structure."]

## Current pressure points
[Update this weekly — what's due soon, what's causing most stress]

## What I've covered with each agent
SAGE: [topics explained so far]
DARWIN: [sources found, research threads active]
QUILL: [essays reviewed, feedback patterns]

## What agents should know about me
[Anything else that helps — e.g. "I tend to ask the same question
multiple ways when I'm confused. Don't give up on me."]
Update this file every Sunday
The profile only works if it reflects where you actually are, not where you were in September. Add it to your weekly routine: 10 minutes every Sunday to update your profile and session log. The agents get measurably better the richer this file becomes.

The session-log.md is simpler — just running notes. After each meaningful session, add a short entry:

memory/session-log.md Example entries 
## 2025-09-14
SAGE explained the Hardy-Weinberg equilibrium — finally got it using
the allele frequency analogy. Still shaky on when to apply it.

## 2025-09-17
DARWIN helped find 4 sources on Cold War proxy conflicts for EE.
Primary source from Kennan archives looks strong. Need to verify date.

## 2025-09-20
QUILL gave feedback on History essay intro — said my thesis doesn't
take a clear enough position. Rewrote it. Much better apparently.

05 / 06
Code
Your first API call

Now we connect everything to Claude. This is the only code you need to understand to build the whole system. Read it slowly — every line has a comment explaining why it's there, not just what it does.

Get your API key first
Go to console.anthropic.com → API Keys → Create Key. Keep it secret — never paste it into public code or push it to GitHub. Store it in a .env file locally.

This is the core function that powers every agent. Understand this and you understand the whole system:

src/agent.js JavaScript 
// Every agent in your team runs through this one function.
// The only thing that changes between agents is:
// 1. The soulContent (who the agent is)
// 2. The profileContent (what the agent knows about you)

async function askAgent(agentName, userMessage, soulContent, profileContent) {

  // Build the system prompt by combining:
  // → the agent's identity (SOUL.md)
  // → everything the agent knows about you (memory files)
  const systemPrompt = `${soulContent}

---
STUDENT PROFILE (read this before every response):
${profileContent}
`;

  // Make the API call to Claude
  const response = await fetch("https://api.anthropic.com/v1/messages", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      // API key goes here — loaded from environment, never hardcoded
      "x-api-key": process.env.ANTHROPIC_API_KEY,
      "anthropic-version": "2023-06-01"
    },
    body: JSON.stringify({
      model: "claude-sonnet-4-20250514",
      max_tokens: 1024,
      system: systemPrompt,         // ← agent identity + your profile
      messages: [
        { role: "user", content: userMessage }  // ← what you just typed
      ]
    })
  });

  const data = await response.json();

  // Extract the text response from Claude's reply
  return data.content[0].text;
}

// Example: ask SAGE a question
// soulContent = contents of agents/sage/SOUL.md
// profileContent = contents of memory/student-profile.md
const reply = await askAgent(
  "sage",
  "I don't understand what activation energy means in Chemistry",
  soulContent,
  profileContent
);

The coordinator (ALEX) needs one extra thing: routing logic. When ALEX gets a message, it decides which agent to call next:

src/coordinator.js JavaScript 
// ALEX receives every message and decides what to do.
// We ask Claude (as ALEX) to return a routing decision,
// then we call the right specialist agent.

async function routeMessage(userMessage) {

  // First: ask ALEX what to do with this message
  const routingPrompt = `
    Based on this message, respond with ONLY one of these words:
    DARWIN, SAGE, QUILL, HAVEN, ATLAS, or SELF
    (SELF means you will handle it directly as ALEX)
    
    Message: "${userMessage}"
  `;

  const decision = await askAgent("alex", routingPrompt, alexSoul, profile);
  const agent = decision.trim().toUpperCase();

  // Second: call the right specialist with the original message
  switch(agent) {
    case "SAGE":   return askAgent("sage",   userMessage, sageSoul,   profile);
    case "DARWIN": return askAgent("darwin", userMessage, darwinSoul, profile);
    case "QUILL":  return askAgent("quill",  userMessage, quillSoul,  profile);
    case "HAVEN":  return askAgent("haven",  userMessage, havenSoul,  profile);
    default:      return askAgent("alex",   userMessage, alexSoul,   profile);
  }
}
Test each agent alone first
Before you build the routing, test each agent's SOUL.md directly. Ask SAGE a question. Check it responds like SAGE should. Ask it something it shouldn't answer — does it refuse? Only wire up the coordinator once each specialist works correctly on its own.

06 / 06
Deploy
Connect everything and go live

The last part is connecting the pieces into a working interface and deploying it. By this point you have: SOUL files for your agents, a student profile in memory, and an understanding of the core API call. Now you build the UI and ship it.

1
Build a minimal chat UI
You only need three elements: a text input for your message, a send button, and a conversation display. Keep it simple — the intelligence is in the agents, not the interface. A clean HTML page with a textarea, a button, and a div that fills with conversation history is enough.
2
Load your files on startup
When the page loads, read all your SOUL.md files and your student-profile.md into JavaScript variables. These get passed into every askAgent() call. In a browser environment, you can store them as JavaScript string constants — or fetch them from your project folder.
3
Wire up the send button
On click: take the message, pass it to routeMessage(), wait for the response, display it in the conversation area. Show which agent responded — e.g. "SAGE →" before the reply. This helps you understand the routing and debug it when something goes to the wrong agent.
4
Keep conversation history
Store a conversationHistory array and pass it back to Claude with each call. This is how Claude remembers what was said earlier in the same session. Each message is {role: "user", content: "..."} or {role: "assistant", content: "..."}. Clear it when you start a new session.
5
Handle the API key safely
Never put your API key in your HTML or JavaScript file. For a Netlify deploy, use Netlify Environment Variables (Site settings → Environment variables) and call the API through a Netlify Function (serverless) that reads the key from process.env. Your key stays private; the browser never sees it.

Deploying to Netlify:

Create a Netlify account at netlify.com — free tier is all you need.
Push your project to GitHub — Netlify connects to your repo and auto-deploys on every commit.
Add your API key — Site settings → Environment variables → Add ANTHROPIC_API_KEY.
Create a Netlify Function in netlify/functions/chat.js — this is your secure API proxy that the browser calls.
Deploy — push to main and your site is live at yourname.netlify.app in about 30 seconds.
What does a good first week look like?
Use it for real studying — not just to test. Ask SAGE something you're actually stuck on. Update your session log after. Notice what the agents do well and what feels off. Your first round of corrections to the SOUL files will be the most valuable thing you do in the whole project.
